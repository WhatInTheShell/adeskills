# Sumo Logic — Detection-Logic Bug Patterns

Platform-specific pitfalls for Sumo Logic detection content across its two distinct surfaces: **Log Search** (the pipeline query language behind saved searches, scheduled searches and Monitors) and **Cloud SIEM** (the rule expression language that runs over normalized records and emits signals). Sumo Logic's distinctive hazard is that **the extraction stage is also a filter**: in every other platform in this catalog a failed field extraction leaves a field absent, and the rule then misbehaves on an absent field — in Sumo Logic a `parse` that does not match removes the message from the pipeline entirely, before any detection logic sees it. Its second distinctive hazard is that **a rule firing is not an alert**: Cloud SIEM signals only become an insight once an entity's accumulated activity score exceeds a threshold, so a correct rule that fires once can be correct and silent at the same time. Pair with [`logging_assumption_errors.md`](logging_assumption_errors.md) and, for transpiled rules, [`sigma.md`](sigma.md).

> **Verification footing.** This is the weakest footing in this catalog and is stated rather than hidden. **No live Sumo Logic tenant exists**, so nothing here is replayed — weaker than [`splunk.md`](splunk.md), whose claims were replayed on Splunk Enterprise 10.4.2. It is also weaker than [`logscale.md`](logscale.md) on the corpus side: **there is no public Sumo Logic rule corpus.** `SumoLogic/cse-rules` does not exist (404, checked 2026-10-16), and the community repo [`SumoLogic/sumologic-content`](https://github.com/SumoLogic/sumologic-content) @ `ce2e5ec` (2026-06-23) turns out not to be one — its `CloudSIEM/` tree holds parsers, log mappings and a single monitor, and its 83 saved searches are overwhelmingly dashboard panels and field-extraction helpers, of which **0 carry a schedule**. Consequently: every **Log Search** claim below is quoted from Sumo Logic's own documentation and, where a `Seen in:` appears, confirmed by reading that query's source; every **Cloud SIEM** claim is **doc-only**, with no rule content to read. If you have a tenant, each claim is a one-event test away from being your own.

## Content shapes and where each one breaks

| Shape | Where it lives | Primary exposure |
|---|---|---|
| Saved searches (dashboard panels) | app content, `Sumo_Logic_Log_Searching/` | ADE4-01 parse drops; no alert contract — an analyst must look |
| Scheduled searches / Monitors | tenant-side; **0 of 83 in the public corpus** | ADE3-03 schedule-vs-window gaps, ADE3-06 result ceilings |
| Scheduled searches that emit Cloud SIEM signals | `stage` / `normalizedSeverity` fields in the query | ADE3-02 activity-score threshold, ADE3-03 signal suppression |
| Cloud SIEM rules (match, threshold, chain, aggregation, outlier, first-seen) | tenant-side; **no public corpus** | ADE4-04 null comparisons, ADE2-02 schema mapping |
| Parsers and log mappings | `CloudSIEM/CSE_Vendor_Content/` | ADE2-02 — the mapping decides which fields exist at all |

## 1. A `parse` without `nodrop` is an undeclared filter (ADE4-01, ADE2-02)

The rule is stated once and applies everywhere: *"For all parse operators, messages must match at least one segment of the parse expression or they are dropped from the results"* ([parse nodrop option](https://www.sumologic.com/help/docs/search/search-query-language/parse-operators/parse-nodrop-option/)). `nodrop` *"forces results to also include messages that do not match any segment of the parse expression"*, and those messages *"are included in the output but do not contain any alias fields or tags related to the parse expression"*. This inverts the failure mode every other platform in this catalog has: elsewhere a broken extraction leaves a field absent and the rule evaluates badly on absence; here the event is gone before the detection logic runs, so the rule reports quiet rather than wrong. A log-format change upstream, a vendor adding a field, or a pattern literal that requires a space the message does not have, all produce the same symptom — zero results and no error. Note also that `nodrop` *"is not supported with the csv, split, parseDate, or parseHex operators"*, so those stages cannot be made non-dropping at all.

Seen in: *Suspicious Traffic: GeoLocation Lookup Mismatch* (Fortinet). The author's intent is unambiguous — **39 of its 41 `parse` stages carry `nodrop`** — and exactly two do not: `parse " dstip=* " as dstip` and `parse "srcip=* " as srcip`. Any FortiGate message whose text does not present those two literals, including the surrounding spaces the patterns require, is discarded. `srcip` is only a `count by` key, not an input to the mismatch test (`where dstcountry != country_name`), so the second omission narrows the detection on a field its own claim does not need. Across the corpus the idiom is near-universal and the exceptions are the finding: **1,148 of 1,190 extraction stages carry `nodrop`; 42 are bare, in 27 of the 83 saved searches.**

**Mitigation:** default to `nodrop` on every extraction stage and make field *requirements* explicit downstream with `where !isNull(field)`, so the dependency is visible and auditable instead of implicit in a pattern literal; reserve a bare `parse` for the case where dropping is the documented intent, and say so in the query. See [ADE4-01 gate inversion](../ade_framework/ADE4/ADE4-01-gate-inversion/gate-inversion.md).

## 2. Keyword terms are case-insensitive; field comparisons are not (ADE1-01)

The two halves of a Log Search query disagree. In the search scope, *"Keyword expressions are case-insensitive"* ([Keyword Search Expressions](https://www.sumologic.com/help/docs/search/get-started-with-search/build-search/keyword-search-expressions/)), as are metadata tags such as `_sourceCategory`. Past the first pipe the opposite holds: `toLowerCase`/`toUpperCase` exist precisely because *"These conditions are case-sensitive in Sumo Logic"*, said of `=` and `!=` ([toLowerCase, toUpperCase](https://www.sumologic.com/help/docs/search/search-query-language/search-operators/tolowercase-touppercase/)), and `matches` is likewise *"case-sensitive"* ([matches](https://www.sumologic.com/help/docs/search/search-query-language/search-operators/matches/)). This is the same positional hazard as SPL's `search`-versus-`where` split ([`splunk.md`](splunk.md) #1), with different operators: a predicate that is forgiving as a keyword becomes exact when moved into a `where`, and the move is the kind of edit that looks like a refactor.

Seen in: *Cortex XDR Scheduled Search*, whose severity ladder uses **two casing conventions in four consecutive arms** — `if(severity = "low", 5, ...)` and `if(severity = "medium", 10, ...)` against `if(severity = "High", 10, ...)` and `if(severity = "Critical", 10, ...)`. Because `=` is case-sensitive, at most one convention can match whatever the source actually emits; the arms in the other convention are dead, and every event they should have scored falls through to the query's own default of `1 as normalizedSeverity`. Compounded by #7, that converts a high-severity alert into a signal contributing 1 point toward a threshold of 12.

**Mitigation:** normalize before comparing — `toLowerCase(field) = "high"` — or compare with a case-folded regex; never let a value literal's capitalization carry detection logic. When auditing, read every `=`, `!=` and `matches` as a case test and ask what the source actually emits.

## 3. A keyword wildcard matches whole terms, and its scope is the entire message (ADE1-01)

Keyword matching is term-based, not substring-based. The raw message is broken into terms at *"white space, dashes, commas, question marks, exclamation points, brackets, and more"*, and *"you need to provide keywords in your query that specifically match those terms"*; a wildcard *"represents zero or more characters"* but only across whole terms — `jsmith@*.com` works while a partial term such as `jsmith@some*re.com` does not, and *"The wildcard (`*`) will only represent one individual full term between supplied values, so if additional terms exist between the defined values, the search will return no results"* ([Keyword Search Expressions](https://www.sumologic.com/help/docs/search/get-started-with-search/build-search/keyword-search-expressions/)). An engineer importing the `*evil*` habit from a substring-matching platform therefore writes something that looks like a broad filter and is not. Metadata adds a second constraint: wildcards and quotes cannot be combined, so a `_sourceCategory` containing spaces cannot be matched loosely — and a renamed source category silently scopes a detection to nothing.

Seen in: *Suspicious Traffic: GeoLocation Lookup Mismatch*, scoped `(_sourceCategory=*fortigate* !(vpn))`. The negation is a bare keyword, so it applies to the **whole raw message**, case-insensitively, not to a field: any traffic log that merely contains the term `vpn` anywhere — an interface or policy named `VPN`, a hostname like `vpn-gw`, a URL path — is excluded from the detection, whether or not it is VPN traffic.

**Mitigation:** keep keyword terms as a coarse index prefilter and put real selection in typed `where` clauses over parsed fields; never express an exclusion as a bare negated keyword when you mean "this field is not that value". Confirm every `_sourceCategory` scope resolves to live data before trusting a zero-result query.

## 4. Three regex flavors and one case-sensitive key reference (ADE1-01, ADE4-03)

Patterns are not portable within the product, let alone into it. In Log Search, `matches` requires patterns that are *"RE2-compliant"* ([matches](https://www.sumologic.com/help/docs/search/search-query-language/search-operators/matches/)). In Cloud SIEM rule expressions, `rlike` accepts a *"Java regular expression"* while `matches` again takes RE2 wildcard-or-regex forms, and `like` is SQL-style with `_` and `%` as its wildcards ([Cloud SIEM Rules Syntax](https://www.sumologic.com/help/docs/cse/rules/cse-rules-syntax/)). RE2 has no backreferences or lookaround; a pattern lifted from a PCRE source may fail to compile, or — worse for a false negative — compile under a different flavor's semantics. Key references are a quieter instance of the same class: *"References to specific keys are case sensitive in a standard JSON operation. For example, if a key name is `sourceIpAddress` and you run `| json "sourceipaddress"` the operation will not return results"*, whereas *"When using the auto option the keys are not case sensitive"* ([Parse JSON Formatted Logs](https://www.sumologic.com/help/docs/search/search-query-language/parse-operators/parse-json-formatted-logs/)). A mis-cased key in an explicit `json` extracts nothing, and under #1 that can discard the message outright.

**Mitigation:** record which engine each pattern targets next to the pattern, and re-verify rather than re-paste when moving between Log Search and Cloud SIEM or in from Sigma; prefer `json auto` where key casing is not guaranteed stable, and pair any explicit `json` with `nodrop`.

## 5. In Cloud SIEM every comparison against a null field returns false — and `!=` is undocumented (ADE4-04)

The rule-expression reference is explicit and uniform: the `=` function returns *"false if either expression is null"*, and the documented examples run the same way throughout — `null = "foo"` returns false, `null < 10` returns false, `10 > null` returns false, `null >= 10` returns false, and `null IN ("value1", "value2", "value3")` returns false. `like` behaves differently again: *"If `pattern` or `escape_character` is null, the expression evaluates to null"* ([Cloud SIEM Rules Syntax](https://www.sumologic.com/help/docs/cse/rules/cse-rules-syntax/)). So every positive filter in a rule expression is silently also a presence test, exactly as in LQL — but **the behavior of `!=` on a null field is not documented**, and that is the one operator whose answer decides whether an exclusion keeps or drops records with the field missing. Splunk documents it (`!=` drops them); LogScale documents it (`!=` matches them); Sumo Logic's reference does not state it in either direction. Marked here as a documentation gap rather than inferred, because the inference is not safe: `like` already shows the product does not uniformly collapse null to false.

**Mitigation:** test `!=` against a record with the field absent on your own tenant before relying on an exclusion, and until then write exclusions as `isNull(field) || field != "value"` so the intended treatment of absence is explicit in the rule rather than inherited from an undocumented default. Assert presence with `!isNull(field)` wherever the rule genuinely requires a field. See [ADE4-04 absent-field inversion](../ade_framework/ADE4/ADE4-04-field-mismapping-semantics/absent-field-inverts-filter.md).

## 6. Cloud SIEM rules see the normalized schema, not the log (ADE2-02)

Rules evaluate normalized records, and normalization is a configuration, not a property of the data: fields reach a rule only if a parser extracted them and a log mapping mapped them to schema attributes. Fields that were parsed but not mapped are *"retained in the fields attribute of the resulting records"* and must be reached explicitly — `fields['parsed-field_name'] = "value of interest"` — or via the `json` operator, whose documented primary use is accessing *"unmapped message fields that are contained in the Cloud SIEM fields attribute"* ([Create a Structured Log Mapping](https://www.sumologic.com/help/docs/cse/schema/create-structured-log-mapping/), [Cloud SIEM Rules Syntax](https://www.sumologic.com/help/docs/cse/rules/cse-rules-syntax/)). A rule naming a normalized field that this tenant's mapping never populates is not an error — it is a rule that matches nothing, and by #5 it fails closed with no diagnostic. This is the Sumo Logic form of the CIM-compliance assumption in [`splunk.md`](splunk.md): content written against a schema, deployed onto a mapping that may not fill it.

**Mitigation:** for every field a rule depends on, confirm the mapping populates it for *this* source — not that the vendor's logs contain it; monitor record volume per normalized field so a mapping regression is visible as a drop rather than as quiet; prefer `fields[...]` with an explicit presence check over a normalized field whose population you have not verified.

## 7. A signal is not an alert: the activity score must *exceed* 12 (ADE3-02)

Cloud SIEM separates firing from alerting, and the gap is where correct rules go silent. A matching record produces a signal whose *"severity score is a number between 0 and 10"*; an entity's activity score is *"the sum of the severities of the unique signals associated with that entity during the previous two weeks"*; and an insight is generated only when that score *exceeds* the threshold — by default *"the detection window is 14 days"* and *"the threshold activity score is 12"* ([Insight Generation Process](https://www.sumologic.com/help/docs/cse/get-started-with-cloud-siem/insight-generation-process/), [Set Insight Generation Window and Threshold](https://www.sumologic.com/help/docs/cse/records-signals-entities-insights/set-insight-generation-window-threshold/)). Because the per-signal ceiling is 10 and the threshold is 12 and must be exceeded, **no single signal of any severity can generate an insight on its own.** A rule can be written correctly, match the record it was designed for, emit a maximum-severity signal, and produce no alert — the detection's real contract is "this plus at least one other distinct signal on the same entity". Every severity assignment is therefore detection logic, which is what makes #2's dead ladder arms expensive rather than cosmetic.

**Mitigation:** state the alert contract alongside the rule — which other signals the entity is expected to accumulate, or that this rule is deliberately a contributor rather than an alert; use a custom insight for the cases that must alert standalone; treat any severity-scoring expression as logic to be reviewed and tested, not metadata.

## 8. Redundant signals are suppressed for 72 hours, so repetition does not accumulate (ADE3-03)

By default *"redundant signals for a signal-entity combination are automatically suppressed for a maximum period of 72 hours to avoid repeated signals contributing to insight generation"* ([Set Insight Generation Window and Threshold](https://www.sumologic.com/help/docs/cse/records-signals-entities-insights/set-insight-generation-window-threshold/)). Combined with #7 this is a precise constraint on what Cloud SIEM can detect: repetition of *one* behavior on *one* entity contributes its severity once per three days no matter how many times it recurs, so an attacker repeating a single detected action cannot be escalated by volume — only breadth across distinct signals accumulates. A threshold tuned on the assumption that a noisy technique will "add up" is tuned against the platform's actual arithmetic.

Corroborated in corpus content rather than inferred: the author of *Cortex XDR Scheduled Search* documents the same behavior in the query header — *"signals with the same name/entity will be auto suppressed. So I recommend creating a custom rule that dynamically changes the name of the Signal to precvent this"* [sic] — which is a workaround for exactly this suppression, and one that works by defeating the deduplication the platform applies deliberately.

**Mitigation:** build escalation out of *distinct* signals on the same entity rather than repetition of one; where repetition is itself the finding, express it inside a single threshold rule's count (which counts records, not signals) instead of expecting the insight layer to tally; review any renaming-to-defeat-suppression construct as a deliberate trade of noise for escalation.

## 9. Result ceilings, and two counts that are estimates (ADE3-06)

Three documented ceilings sit under Log Search aggregation. `limit` *"supports requests for up to 10,000 results"*, and once an aggregation is present it reduces grouped results rather than raw ones ([limit](https://www.sumologic.com/help/docs/search/search-query-language/search-operators/limit/)). `count_frequent` exists for aggregations with *"over 10,000 distinct groups"* and *"returns the highest-count 10,000 results in sorted order"*, most-to-least — value-ranked retention, so as in LQL's `groupBy()` the rare groups a rarity gate selects *for* are the first evicted — and its output field is named `_approxcount` because it is *"only an estimate of the true count; the estimate may be incorrect, but can only be over (it will never be under)"*. `count_distinct` is approximate too, above 100 distinct items using *"an approximate algorithm"* with documented bands — *"65% of the time, results are within +/- 2%"*, 95% within ±4%, 99% within ±6% ([count, count_distinct, count_frequent](https://www.sumologic.com/help/docs/search/search-query-language/group-aggregate-operators/count-count-distinct-and-count-frequent/)). A threshold compared against `count_distinct` is therefore a threshold compared against an estimate that can err in **both** directions, unlike `_approxcount`, which can only overstate.

The counter-lesson, in the spirit of [`logscale.md`](logscale.md) #9: the corpus's three `count_distinct` uses are **not** findings. *MWG-006 Users with Multiple Source IP* and *MWG-007 IP Address Used by Multiple People* gate on `_count_distinct > 1`, and the approximation only engages above 100 distinct items, so the gate is structurally out of its reach. A ceiling is only a finding when the data can actually reach it — audit the pipeline before filing.

**Mitigation:** never compare a tuned threshold against `count_distinct` where the distinct count can exceed 100 — count exactly over a narrowed key, or widen the margin to swallow ±6%; set `limit` explicitly on anything scheduled; and treat `count_frequent` as unusable for rarity detection, since its retention policy is the opposite of what rarity needs.

## Quick audit checklist for Sumo Logic content

- Does every extraction stage carry `nodrop` — and for the ones that do not, is dropping the documented intent? (`csv`, `split`, `parseDate`, `parseHex` cannot carry it at all.)
- Is any value literal's capitalization carrying logic? Keyword terms are case-insensitive; `=`, `!=` and `matches` are not. Check every severity or category ladder for mixed conventions.
- Is any keyword wildcard being used as a substring match? It matches whole terms only. Is any exclusion written as a negated bare keyword, scoping it to the whole message rather than a field?
- Does every explicit `json` key match the source's casing exactly, and is it paired with `nodrop`?
- Which regex engine does each pattern target — RE2 (`matches`), Java (`rlike`), or SQL wildcards (`like`)?
- In Cloud SIEM: which positive filters are silently presence tests? Has `!=` on an absent field been tested on this tenant, or is the rule relying on an undocumented default?
- Does this tenant's log mapping actually populate every normalized field the rule names?
- What is this rule's real alert contract? A single signal cannot exceed the activity-score threshold of 12, and a repeat of the same signal on the same entity is suppressed for 72 hours.
- Can the data reach the ceiling or the approximation you are about to flag? `count_distinct` is only approximate above 100 distinct items.
